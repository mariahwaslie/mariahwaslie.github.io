Loan Default Risk Scoring — End-to-End ML System
Full-stack credit risk system with a trained CatBoost model, FastAPI inference API, React+TypeScript frontend, Docker deployment, and CI/CD pipeline.

Problem

Predict loan defaults on 1.27M real LendingClub records — and build a production inference system around the model, not just a notebook.

What I Built
  • Trained CatBoost, LightGBM, XGBoost, and Logistic Regression with strict temporal splits (train 2012-16, validate 2017, test 2018)
  • Reduced features from 93 to 75 using SHAP importance — improved generalization
  • Applied isotonic calibration for honest probabilities, optimized threshold at 0.2625 via F1
  • Built secondary ML model to predict missing DTI values instead of naive imputation
Key Engineering Decision

The raw dataset contained post-origination features (payment history, recovery amounts, future FICO updates) that would inflate accuracy to 95%+ but produce a useless model in production. I audited all 93 features for temporal leakage before any modeling — removing 18 features. This matters more than any hyperparameter tuning.

Engineering
  • FastAPI backend with Pydantic schema validation (75-feature input), structured logging per inference request, and error handling with trace logging
  • React + TypeScript frontend with interactive sliders for real-time risk prediction — adjust borrower features and see live probability updates
  • Docker Compose multi-service deployment (frontend on port 5173, backend on port 8000)
  • GitHub Actions CI running pytest for model loading, prediction pipeline, and API stability on every push

Clinical Risk Platform — FHIR-Compliant Healthcare System
Multi-service healthcare platform: Java/Spring Boot API following FHIR interoperability standards, Python ML service for clinical deterioration prediction, with Docker and CI/CD.
Problem & Architecture

Healthcare systems need early warning for patient deterioration, but clinical data follows strict interoperability standards (HL7 FHIR) that most ML projects ignore. I'm building a platform that takes this seriously — structuring all data as proper FHIR resources (Patient, Observation, Condition, Encounter) with LOINC and ICD-10 coding, the same standards used by Epic, Cerner, and every modern EHR.

Completed: Spring Boot REST API with FHIR endpoints and JWT authentication, data loading from Synthea. Currently: data preparation and cleaning pipelines for time-series vital sign analysis. Planned: LightGBM deterioration prediction, content-based intervention recommender, PySpark pipeline into Snowflake, Tableau + Power BI dashboards.

Why This Architecture
  • Chose FHIR resource structure because every major EHR vendor (Epic, Cerner) now exposes data through FHIR APIs — this isn't academic, it's how production healthcare data works
  • Java/Spring Boot for the API layer because healthcare enterprise systems run on Java, and Spring Boot is the standard framework
  • Separate Python ML service (FastAPI) for model serving — isolating inference from the API follows microservice best practices and allows independent scaling
  • Planning PySpark for feature engineering because MIMIC-III CHARTEVENTS (330M+ rows of vital signs) is genuinely too large for Pandas
